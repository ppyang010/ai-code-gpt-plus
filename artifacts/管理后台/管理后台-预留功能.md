# 管理后台 预留功能文档

最后更新：2026-05-31

## 文档说明

- 本文档用于单独记录管理后台首版预留但不实现的功能。
- 本文档不作为当前实现任务清单，不进入 `管理后台-task.md` 的 P0-P3。
- 后续如果决定实现本文档中的某个能力，需要先回写 `管理后台-desgin.md`，再同步 `管理后台-task.md`。
- 配套设计文档：`管理后台-desgin.md`
- 配套任务跟踪文档：`管理后台-task.md`

## 首版不做原则

- 不影响首版运营配置后台闭环的能力，先预留，不进入当前开发。
- 会显著改变权限模型、数据一致性、支付资金流、运行时配置生效方式的能力，必须单独设计后再实现。
- 当前代码尚缺基础链路的能力，不在后台里先做“看起来可操作但实际不闭环”的入口。

## 预留功能清单

| 预留功能 | 首版不做原因 | 当前预留点 | 后续触发条件 |
| --- | --- | --- | --- |
| 模型供应商配置热生效 | 当前 OpenAI-compatible 客户端可用性仍由本地配置判断，直接做 DB CRUD 容易让用户误以为已影响运行时 | `model_provider.base_url`、`model_provider.api_key_encrypted`、`model_provider.default_headers` | 需要后台修改供应商后不重启服务即可影响模型调用 |
| 模型配置运行时刷新 | 模型列表可从 DB 读，但模型客户端路由、密钥和供应商能力不完全由 DB 驱动 | `model_config.status`、`model_config.extra_config` | 需要新增/停用模型后立即影响聊天发送链路 |
| 供应商连接测试 | 测试连接需要真实调用外部供应商，会引入网络、密钥、额度和错误分类问题 | 模型供应商详情页可预留“测试连接”按钮位置 | 供应商配置管理稳定后，需要管理员验证密钥和 baseUrl 可用 |
| API Key 轮换和密钥版本 | 首版只要求写入和脱敏展示，轮换会引入多版本、灰度和回滚逻辑 | `api_key_encrypted` 字段可先承载当前密钥 | 需要无中断轮换供应商密钥或保留历史密钥版本 |
| 角色权限矩阵 RBAC | 首版只有管理员身份；RBAC 会增加角色、权限点、菜单权限和接口权限维护成本 | `admin_user` 可后续扩展 `role_id` 或关联角色表 | 后台用户超过单一管理员角色，需要区分运营、财务、技术管理员 |
| 菜单权限管理 | 依赖 RBAC，首版固定后台菜单即可 | 前端 `/admin/**` 路由和侧边导航 | 需要按管理员角色动态展示菜单 |
| 后台操作日志中心 | 首版只要求登录日志，完整审计会新增表、详情页和操作埋点规范 | 可后续新增 `admin_operation_log` | 模型、提示词、用户状态等敏感操作需要可追溯审计 |
| 普通用户登录鉴权接入 | 当前用户侧仍使用临时 `X-User-Id`，后台只管理 `app_user.status` 无法完整阻断访问 | `app_user.status` | 用户侧登录注册和 token 鉴权进入实现阶段 |
| 普通用户注册/找回密码 | 管理后台只做用户管理视角，不承担用户侧账号流程 | `app_user` 表已有账号字段 | 面向真实用户开放注册登录 |
| 余额扣减和额度拦截 | 当前 `user_balance` 和 `user_token_usage` 首版只记录和展示，扣费会影响聊天发送主链路 | `user_balance`、`user_token_usage` | 需要按余额、套餐或 token 限额控制用户调用 |
| 充值订单和支付闭环 | 涉及支付渠道、订单状态机、回调验签和资金安全，不能作为后台附属 CRUD | 文档已预留 `recharge_order` | 需要上线真实充值或套餐售卖 |
| 财务对账和退款 | 依赖充值订单和支付闭环，首版没有资金流 | 后续支付模块 | 支付上线后需要运营或财务处理对账、退款 |
| 多维用量报表大屏 | 首版只做日志和用量只读查询，大屏会增加聚合口径、缓存和图表设计 | `api_call_log`、`user_token_usage` | 需要运营按日、模型、供应商、用户观察趋势 |
| 成本价格配置 | 预估成本字段已存在，但首版不维护计价规则，避免展示不可信成本 | `estimated_cost`、模型配置扩展字段 | 需要按供应商和模型维护输入/输出 token 单价 |
| 提示词多层级模板 | 首版只做快速/思考默认模板；按模型、场景、租户分层会改变提示词解析优先级 | `prompt_template` 可预留 `scope_type`、`scope_id` 扩展 | 需要不同模型、场景或用户群使用不同系统提示词 |
| 提示词版本管理和发布 | 首版编辑即保存；版本发布会引入草稿、发布、回滚和生效范围 | `prompt_template` | 提示词需要灰度、回滚或审计历史 |
| 模板效果评估 | 需要关联会话质量、人工标注或 A/B 实验，当前没有评价数据 | 聊天消息和调用日志 | 需要比较不同提示词模板的效果 |
| 文件资源后台管理 | 当前只接入聊天图片上传，通用文件上传仍是后续扩展 | `file_asset` | 需要管理员查看、删除、冻结用户上传资源 |
| 内容安全审核 | 需要接入审核策略、拦截记录和人工处理流程 | 聊天消息、文件资源 | 需要对用户输入、模型输出或图片做安全管控 |
| 系统配置中心 | 首版只做模型和提示词配置，通用配置中心会扩大后台边界 | 可后续新增系统配置表 | 需要后台维护全局开关、限制、公告等配置 |
| 公告和站内通知 | 当前产品主线是聊天功能，没有通知体系 | 前端布局可后续预留入口 | 需要向普通用户展示系统公告或运营通知 |
| 多租户管理 | 当前数据结构按单站点设计，没有租户字段 | 后续可能给核心表补 `tenant_id` | 需要服务多个组织、团队或客户 |
| 后台导入导出 | 需要定义导出权限、脱敏规则和大数据量处理 | 用户、日志、用量列表页 | 管理员需要批量导出用户、调用日志或用量报表 |
| 后台国际化 | 当前项目文案以中文为主，首版不引入 i18n 成本 | 前端文案集中度可后续优化 | 后台需要支持多语言管理员 |
| 构建发布管理页 | 当前发布流程不属于业务后台，放入后台会混淆运维边界 | 项目脚本和部署文档 | 需要在平台内展示版本、构建或发布状态 |

## 后续升级顺序建议

1. 先补用户侧登录鉴权，让普通用户状态管理具备真实拦截效果。
2. 再补模型供应商动态配置刷新，解决 DB 配置和运行时生效之间的差距。
3. 然后补后台操作日志和 RBAC，增强后台安全边界。
4. 最后推进额度扣减、充值订单、财务对账等资金相关能力。

## 不进入首版任务的验收口径

- 首版后台页面中不出现尚未闭环的操作按钮，例如“立即生效”“测试连接”“扣费”“退款”“发布模板版本”。
- 如果页面需要展示预留能力，只能以只读提示或禁用状态出现，不能让管理员误以为功能已经可用。
- 后续启用任一预留功能前，必须补充设计、任务拆分、DDL/DML、接口契约、接口逻辑和测试用例。
