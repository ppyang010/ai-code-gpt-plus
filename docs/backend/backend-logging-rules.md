# GPT Plus 后端日志规范

最后更新：2026-05-28

## 目的

这份规范用于统一 `gpt-plus-core` 的基础日志口径，先解决三个问题：

- 关键链路出了问题时，日志里能快速定位到用户、会话、消息和模型
- 可恢复异常与真正的系统故障分层输出，避免全都打成同一种错误
- 避免把密钥、完整提示词、完整聊天内容等敏感信息直接写进日志

## 级别约定

### `DEBUG`

用于只读查询和低风险排查信息，例如：

- 分页列表查询
- 模型列表读取
- 不影响主流程的附属统计

默认环境下 `root` 为 `info`，因此这类日志可以保留但不默认刷屏。

### `INFO`

用于关键业务动作的开始、完成和状态变更，例如：

- 创建 / 修改 / 删除会话
- 发送消息、继续生成进入异步流
- 图片上传成功
- 模型流式调用完成

### `WARN`

用于可恢复异常或已知异常分支，例如：

- 参数校验失败、请求体解析失败
- 业务异常
- 客户端主动中断 SSE
- 上传临时文件清理失败
- 流式输出中断但已有可恢复内容

### `ERROR`

用于真正的系统故障或未兜住的异常，例如：

- 未处理异常导致返回通用 5xx
- 模型流在没有可恢复内容时直接失败
- 会影响本次业务正确性的非预期异常

## 推荐字段

关键链路日志优先带这些字段，至少保证排查能串起来：

- `userId`
- `sessionId`
- `messageId`
- `modelId`
- `modelCode`
- `fileId`
- `elapsedMs`
- `totalTokens`
- `finishReason`

如果某个字段当前场景拿不到，可以省略，但不要为了凑字段额外查库。

## 禁止输出的内容

以下内容不要直接打到日志里：

- API Key、Authorization、Cookie、用户凭证
- 完整 `systemPrompt`
- 完整用户输入、完整 assistant 输出
- 原始图片或文件内容
- 原始供应商请求 / 响应 payload

如果确实需要辅助排查，优先记录：

- 文本长度
- 附件数量
- 模型码值
- 错误码
- HTTP 状态码

## 第一版落地点

这一版先覆盖最核心的几条链路：

- `GlobalExceptionHandler`：统一记录业务异常、参数异常、请求解析异常和未处理异常
- `ChatSessionServiceImpl`：记录会话创建、改名、删除和分页查询
- `ChatMessageServiceImpl`：记录发送消息、继续生成、流式开始、成功结束和异常结束
- `FileAssetServiceImpl`：记录图片上传成功和文件清理失败

后续如果继续补 provider 级日志，再把外部模型调用适配器一起纳入。
